# API garage

Справочник HTTP API сервера garage, версия 1.0: учётные записи, сессии и приглашения (ФТ-1), справочники, позиции, склад, покупки, расход, список покупок и шаблоны расхода (ФТ-2…ФТ-8). Сервер — `internal/web`, клиент — интерфейс `web/src`. Документ описывает текущее поведение кода; при расхождении источник истины — код.

## Общие правила

### Формат

- Все адреса API начинаются с `/api/`. Тела запросов и ответов — JSON в UTF-8 (`Content-Type: application/json; charset=utf-8`). У всех ответов API `Cache-Control: no-store`.
- Неизвестные поля в теле запроса игнорируются. Тело — не больше 64 КБ, иначе `413 {"error": "Слишком большой запрос"}`. Битый JSON или поле не того типа — `400 {"error": "Неверный формат запроса"}`.
- **Деньги** — целые копейки (`119000` = 1 190 ₽).
- **Количество** — целое число в единице позиции: мл (`unit: "ml"`) или шт (`unit: "pcs"`). Дробей нет.
- **Время** — секунды Unix (UTC), поля с суффиксом `_at`.
- **Даты покупок** — строка `"ГГГГ-ММ-ДД"`.
- Списки отдаются объектом с одним массивом: `{"categories": […]}`, `{"products": […]}` и т. д. Пустой список — `[]`, не `null`.
- Поле, которого может не быть, приходит как `null` (не пропускается). Исключение — `price_per_100`/`price_per_unit` у `PurchaseRow`: выводится только одно из двух.
- Неизвестный адрес под `/api/` — `404 {"error": "Нет такого метода API"}`. Неподдерживаемый метод — `405 {"error": "Метод не поддерживается"}` с заголовком `Allow`. Где есть `GET`, работает и `HEAD`.
- `{id}` в адресе — положительное целое; иначе `404` с тем же текстом, что и для несуществующей записи.

### Ошибки

Код HTTP и тело:

```json
{ "error": "Текст для человека по-русски", "field": "login" }
```

- `error` можно показывать пользователю как есть.
- `field` — имя поля формы, к которому относится ошибка; есть не всегда.
- Дополнительные поля: `retry_after` (секунды) у `429`, `available` у `409` при нехватке остатка.

| Код | Когда |
|---|---|
| `400` | Ввод не прошёл проверку (почти всегда с `field`), битый JSON, неверный параметр запроса |
| `401` | `{"error": "Нужно войти"}` — нет сессии или она истекла; неверный логин или пароль при входе |
| `403` | `{"error": "Запрос отклонён"}` — нет CSRF-заголовка; `{"error": "Доступно только владельцу"}`; неверный текущий пароль при смене |
| `404` | Записи нет **или она чужая** — ответ одинаковый |
| `405` | Метод не поддерживается адресом |
| `409` | Конфликт с состоянием данных: занятое имя, нехватка остатка, закончившийся экземпляр, архив места с экземплярами |
| `413` | Тело больше 64 КБ |
| `429` | Превышено число попыток входа |
| `500` | `{"error": "Внутренняя ошибка сервера"}` — подробности только в журнале сервера |

**Порядок проверок** на каждом адресе: метод (`405`) → CSRF-заголовок (`403`) → сессия (`401`) → права владельца (`403`) → тело и бизнес-проверки.

### Аутентификация и сессия

- Сессия — cookie `garage_session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age` 30 дней, `Secure` (кроме конфигурации с `"insecure_cookies": true` — только для локальной разработки по http). В базе хранится только SHA-256 токена.
- Срок 30 дней продлевается при работе: если с последнего продления прошло больше часа, `expires_at` сдвигается на 30 дней от текущего момента и cookie выставляется заново (ФТ-1.1).
- Пришла cookie с недействительной или истёкшей сессией — ответ `401`, cookie стирается.
- Пароли хранятся хешем argon2id.
- Уровни доступа в справочнике ниже: **без входа**, **с входом** (по умолчанию — если не указано иное), **только владелец** (`is_owner: true`; остальным — `403 {"error": "Доступно только владельцу"}`).

### Защита от CSRF (ТБ-3)

Каждый запрос, кроме `GET`/`HEAD`, обязан нести заголовок `X-Requested-With: garage` — в том числе адреса без входа (`login`, `logout`, принятие приглашения). Без него — `403 {"error": "Запрос отклонён"}`. Чужая страница не может поставить этот заголовок без разрешения CORS, а CORS сервер не разрешает.

### Ограничение попыток входа (ТБ-4)

- 5 неудачных попыток за 15 минут (скользящее окно) — отдельно **на логин** (без учёта регистра) и **на адрес клиента**; блокирует то, что исчерпано раньше.
- Считаются неудачные `POST /api/auth/login` и неверный текущий пароль в `POST /api/auth/password`.
- При блокировке запрос отклоняется до проверки пароля (даже верного): `429 {"error": "Слишком много попыток. Повторите через 12 минут", "retry_after": 720}` и заголовок `Retry-After: 720`. `retry_after` — секунды, в тексте — минуты с округлением вверх.
- Успешный вход (и успешная смена пароля) сбрасывает счётчик логина; счётчик адреса не сбрасывается.
- Счётчики хранятся в памяти и обнуляются при перезапуске сервера.
- **Адрес клиента**: заголовкам прокси верим только если соединение пришло с loopback (nginx на том же сервере). Тогда берётся `X-Real-IP`, иначе правый адрес из `X-Forwarded-For`; с любого другого адреса — `RemoteAddr`, заголовки игнорируются.

### Изоляция пользователей (ТБ-5)

Все данные склада принадлежат пользователю. `user_id` берётся только из сессии, никогда из тела или адреса. Чужой или несуществующий `id` — в адресе, в теле (`product_id`, `location_id`, `store_id`, `unit_id`, `category_id`…) или в параметре `product_id` журнала — даёт одинаковый `404 {"error": "… не найдена"}`, чтобы нельзя было узнать, существует ли чужая запись. Исключение — фильтры списка позиций (`category_id`, `location_id`): чужой id даёт пустой список.

### Заголовки безопасности (ТБ-6)

На всех ответах (API и интерфейс):

```
Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; img-src 'self' blob:; font-src 'self'; connect-src 'self'; manifest-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: same-origin
Cross-Origin-Opener-Policy: same-origin
```

`'wasm-unsafe-eval'` (с версии 1.1) разрешает только компиляцию WebAssembly — модуля сканера штрихкодов `zxing-wasm` (ФТ-9.6); `eval` и `new Function` для скриптов по-прежнему запрещены. Файл модуля лежит в `assets/` рядом с остальной сборкой и отдаётся с `Content-Type: application/wasm`, внешних адресов нет.

`img-src` включает `blob:` (с версии 1.2): без `createImageBitmap` браузер читает снимок перед сжатием через `<img>` по blob-адресу, созданному самой страницей (ФТ-10.4.2). Внешних картинок и `data:` политика по-прежнему не разрешает.

Всё, что вне `/api/`, — файлы интерфейса; неизвестный путь без расширения отдаёт `index.html` (экранами управляет роутер в браузере), отсутствующий файл с расширением — `404`.

## Учётные записи

### Объекты

```json
// User
{ "id": 1, "login": "ringino", "is_owner": true }

// Settings — шаги кнопок количества (ФТ-5.8)
{ "step_small": 10, "step_large": 50 }

// Invite — без токена: токен хранится только хешем и виден один раз, при создании
{ "id": 7, "created_at": 1792140000, "expires_at": 1792744800, "status": "active" }
// status: active | used | expired | revoked (вычисляется: used важнее revoked, revoked важнее expired)
```

### Проверка ввода (ТБ-7)

| Поле | Правило | Ошибка |
|---|---|---|
| `login` | 3–32 символа: латиница, цифры, `_ . -`; уникален без учёта регистра | `400`, `field: "login"`, «Логин — от 3 до 32 символов: латиница, цифры, «_», «.», «-»»; занят — `409 {"error": "Этот логин уже занят", "field": "login"}` |
| `password` | 8–128 символов (считаются символы, не байты), корректный UTF-8 | `400`, `field: "password"`, «Пароль — от 8 до 128 символов» |
| `step_small` | целое 1–1000 | `400`, `field: "step_small"` |
| `step_large` | целое 1–5000, больше `step_small` | `400`, `field: "step_large"` |

## Вход и сессия

### `POST /api/auth/login` — без входа

```json
{ "login": "ringino", "password": "…" }
```

- `200 { "user": User, "settings": Settings }` + cookie сессии.
- `401 {"error": "Неверный логин или пароль"}` — одинаково для несуществующего логина и неверного пароля (время ответа тоже выравнивается).
- `429` — см. «Ограничение попыток входа».
- Логин сравнивается без учёта регистра.

### `GET /api/auth/me`

- `200 { "user": User, "settings": Settings }` или `401`.
- Интерфейс вызывает его при запуске, чтобы понять, показывать вход или приложение.

### `POST /api/auth/logout` — без входа

- Тело не нужно. `204`, сессия из cookie удалена, cookie стёрта. Без сессии — тоже `204`. Ответ несёт `Clear-Site-Data: "cache"`: браузер забывает кэш сайта (фото позиций кэшируются на год), чтобы они не остались на общем устройстве.

### `POST /api/auth/logout-all` (ФТ-1.4)

- `204`, удалены **все** сессии пользователя, включая текущую; cookie стёрта; заголовок `Clear-Site-Data: "cache"`, как у `logout`.

### `POST /api/auth/password` (ФТ-1.4)

```json
{ "current": "…", "new": "…" }
```

- `204`. Остальные сессии пользователя удаляются, текущая остаётся.
- `400` — новый пароль не проходит проверку (`field: "new"`). Проверяется до текущего пароля.
- `403 {"error": "Текущий пароль неверный", "field": "current"}` — `403`, а не `401`, чтобы интерфейс не решил, что сессия кончилась. Неудачи считаются в ограничение попыток по логину пользователя и адресу.
- `429` — исчерпан лимит попыток (проверяется первым).

### `PUT /api/auth/settings`

```json
{ "step_small": 10, "step_large": 50 }
```

- `200 Settings`. Оба поля обязательны (не переданное считается `0` → `400`).

## Приглашения (ФТ-1.3)

### `GET /api/invites` — только владелец

- `200 { "invites": [Invite, …] }` — последние 20 приглашений, созданных текущим владельцем, новые сверху.

### `POST /api/invites` — только владелец

- Тело не нужно. `201 { "invite": Invite, "url": "https://garage.north-flow.online/invite/<token>" }`.
- Токен — 32 случайных байта в base64url. Срок — 7 дней. **Ссылка показывается только в этом ответе**: в базе лежит хеш, восстановить её нельзя. Интерфейс показывает ссылку с кнопкой «Копировать» сразу после создания, а в списке — только срок и статус.
- `url` строится из заголовков запроса: хост — из `Host`; схема — `https`, если запрос пришёл по TLS или через nginx (соединение с loopback и `X-Forwarded-Proto: https`, либо без `X-Forwarded-Proto`, но с `X-Real-IP`/`X-Forwarded-For`); иначе `http` (локальная разработка).

### `DELETE /api/invites/{id}` — только владелец

- `204` — приглашение отозвано (`revoked_at`); повторный отзыв и отзыв истёкшего — тоже `204`.
- `404 {"error": "Приглашение не найдено"}` — нет, уже использовано или создано другим владельцем.

### `GET /api/invites/by-token/{token}` — без входа

- `200 { "expires_at": 1792744800 }` — приглашение действует.
- `404 {"error": "Приглашение не найдено или уже недействительно"}` — нет, истекло, использовано или отозвано.

### `POST /api/invites/by-token/{token}/accept` — без входа

```json
{ "login": "friend", "password": "…" }
```

- `201 { "user": User, "settings": Settings }` + cookie сессии. Новый пользователь — не владелец, со своим пустым складом.
- Ошибки: `404` — приглашение недействительно (проверяется **до** ввода: по мёртвой ссылке ошибок полей не будет); `400` — проверка ввода; `409 {"error": "Этот логин уже занят", "field": "login"}` — приглашение при этом не расходуется.
- Использование приглашения и создание пользователя — одна транзакция: одно приглашение — один пользователь, из двух одновременных принятий успешно ровно одно.
- При создании пользователя (здесь и в `garage user add`) заполняются: настройки `{step_small: 10, step_large: 50}` и категории по умолчанию (ФТ-2.1) в таком порядке — Шампуни `blue`, Активная пена `berry`, Очистители `olive`, Полироли и защита `ochre`, Стёкла `petrol`, Кожа и пластик `plum`, Шины и диски `slate`, Микрофибра `umber`, Губки и аппликаторы `umber`, Щётки `umber`, Прочее `slate`. Места и магазины — пустые.

## Справочники (ФТ-2)

```json
// Category
{ "id": 3, "name": "Шампуни", "color": "blue", "sort": 0, "archived": false, "products_count": 4 }
// Location
{ "id": 5, "name": "Коробка 3", "sort": 2, "archived": false, "units_count": 5, "checked_at": 1792140000 }
// checked_at — когда место проверяли инвентаризацией (unix-секунды); null — не проверялось
// Store
{ "id": 2, "name": "Автохим", "url": "", "archived": false }
```

| Адрес | Что делает |
|---|---|
| `GET /api/categories[?archived=1]` | `200 {categories: [Category]}` по `sort`, затем по имени. Без `archived=1` — только действующие, с ним — все вместе с архивными. `products_count` — неархивные позиции категории |
| `POST /api/categories` `{name, color}` | `201 Category`. `color` — один из восьми: `blue`, `berry`, `olive`, `ochre`, `petrol`, `plum`, `slate`, `umber` (иначе `400`, `field: "color"`); новая — в конец (`sort` = max+1) |
| `PATCH /api/categories/{id}` `{name?, color?, archived?}` | `200 Category`. Архивировать можно всегда: позиции остаются, но в формах архивная категория не предлагается |
| `POST /api/categories/reorder` `{ids: [...]}` | `204`. Новый порядок действующих: `ids` — ровно все действующие категории пользователя, каждая один раз, иначе `400 {"error": "Список устарел: обновите страницу", "field": "ids"}` |
| `GET /api/locations[?archived=1]` → `{locations: [Location]}`, `POST {name}`, `PATCH /{id} {name?, archived?}`, `POST /reorder {ids}` | То же для мест. `units_count` — экземпляры в статусах `sealed`/`open`. **Архивировать место с экземплярами нельзя**: `409 {"error": "В месте лежат экземпляры: 5. Сначала переложите их"}` |
| `GET /api/locations/{id}/units` | Инвентаризация (ФТ-10.1): `200 {units: [InventoryUnit]}` — экземпляры `sealed`/`open` **действующих** позиций в месте: `Unit` + `product: {id, name, brand, unit, package_size}`. Порядок: по названию позиции (регистр различается только у латиницы: сортировка SQLite `NOCASE` не знает кириллицу), вскрытые раньше запечатанных, по `id`. Чужое или несуществующее место — `404`; архивное — пустой список (экземпляры в архивное место класть нельзя) |
| `POST /api/locations/{id}/checked` | Инвентаризация: ставит `checked_at` = сейчас, без тела. `200 Location`. Чужое/несуществующее — `404`, архивное — `409` |
| `GET /api/stores[?archived=1]` → `{stores: [Store]}`, `POST {name, url?}`, `PATCH /{id} {name?, url?, archived?}` | То же для магазинов, порядок — по имени, без `reorder`. `url` — пусто или `http(s)://хост…`, до 500 символов (`400`, `field: "url"`) |

### Назначения (ФТ-15.1, v1.5)

Свой справочник пользователя, как категории, но без цвета. Стартовый набор — «ЛКП», «стекло», «пластик», «кожа», «диски», «шины», «текстиль» (в таком написании): миграция 008 засевает его существующим пользователям, при создании пользователя — новым. Менять набор можно как угодно.

```json
// Purpose
{ "id": 21, "name": "кожа", "sort": 4, "archived": false, "products_count": 3 }
// products_count — неархивные позиции с этим назначением
```

| Адрес | Что делает |
|---|---|
| `GET /api/purposes[?archived=1]` | `200 {purposes: [Purpose]}` по `sort`, затем по имени; без `archived=1` — только действующие, с ним — все вместе с архивными |
| `POST /api/purposes` `{name}` | `201 Purpose`, в конец списка |
| `PATCH /api/purposes/{id}` `{name?, archived?}` | `200 Purpose`. Архивное назначение остаётся у позиций, но новым не назначается |
| `POST /api/purposes/reorder` `{ids: [...]}` | `204`; `ids` — ровно все действующие, иначе `400`, `field: "ids"` |

Правила имён, уникальности (`409`), архива и порядка — те же, что у категорий. Чужое или несуществующее назначение — `404 {"error": "Назначение не найдено"}`.

- Удаления справочников нет — только архив (ФТ-2.4).
- Имена — 1–40 символов после обрезки пробелов по краям (`400`, `field: "name"`).
- Имена уникальны у пользователя **без учёта регистра, включая кириллицу** («Коробка Новая» = «коробка новая») и вместе с архивными: `409 {"error": "Такое название уже есть", "field": "name"}`. Сменить регистр своего имени можно.
- Возврат из архива ставит категорию или место в конец порядка.
- Поля, не относящиеся к справочнику (`color` у места, `url` у категории), игнорируются.
- Проверка «в месте есть экземпляры» атомарна с записью.

`last_consume_qty` — сумма движений последней (по `id`) группы `batch_id` ручного расхода (`POST /api/consume`) этой позиции; расход по шаблону не учитывается; после отмены — предыдущее нажатие; `null` — не списывали.

### Фото позиции (ФТ-10.4)

Одно фото на позицию. Хранится в базе (таблица `product_photos`, миграция 005), поэтому входит в ежедневный снимок и ночную копию. Браузер сжимает снимок до 1024 px по длинной стороне, JPEG не больше 300 КБ; сервер принимает с запасом.

| Адрес | Что делает |
|---|---|
| `PUT /api/products/{id}/photo` | Тело — **сырые байты** изображения (не JSON), `Content-Type` не проверяется. `200 ProductSummary` с новым `photo_updated_at`. Метка всегда строго растёт, в том числе после `DELETE` и нового `PUT` в ту же миллисекунду |
| `GET /api/products/{id}/photo` | Байты фото с `Content-Type` из содержимого (`image/jpeg`, `image/png`, `image/webp`), `Content-Length`, `Cache-Control: private, max-age=31536000, immutable`, `Vary: Cookie`. Клиент строит адрес `…/photo?v=<photo_updated_at>`: при замене адрес меняется и кэш сбрасывается. `HEAD` работает |
| `DELETE /api/products/{id}/photo` | `200 ProductSummary` с `photo_updated_at: null`. Позиция без фото — тоже `200` |

Проверка при `PUT` (и при импорте): тело не пустое; **не больше 400 КБ**; тип определяется по сигнатуре байтов (JPEG `FF D8 FF`, PNG, WebP `RIFF…WEBP`), заголовок запроса не учитывается; размеры берутся из заголовка файла (`VP8`/`VP8L`/`VP8X` у WebP), не больше 4096 × 4096 px.

Ошибки: `400 {"error": "Нужно фото JPEG, PNG или WebP", "field": "photo"}` (другой тип, битый заголовок, пустое тело — «Фото не передано»); `400 {"error": "Фото больше 4096 × 4096 px", "field": "photo"}`; `413 {"error": "Фото больше 400 КБ", "field": "photo"}`; чужая и несуществующая позиция, а для `GET` ещё и позиция без фото — одинаковый `404`. Предел тела 400 КБ действует только на этом адресе (на остальных — 64 КБ). Через nginx проходит без настройки (предел nginx по умолчанию — 1 МБ).

Архив позиции только скрывает её из списка позиций, из «мало» в списке покупок и из подсказок брендов. Архивную позицию по-прежнему можно купить, израсходовать, списать, добавить в шаблон и в список покупок — сервер её не отклоняет.

Текстовые поля обрезаются по краям. Проверка «есть экземпляры» и смена `unit` атомарны с записью.

| Поле | Правило | Ошибка |
|---|---|---|

```json

  "created_at": 1792000000 }

// PurchaseShort
{ "id": 8, "date": "2026-10-02", "store": "Автохим", "total": 238000, "lines_count": 1 }
```

Отмены покупки целиком нет (Р-13): ошибки исправляются корректировкой и списанием.

**Ввод имеющегося остатка** `POST /api/units` `{product_id, remaining_qty, initial_qty?, location_id?}`:

- `initial_qty` по умолчанию — `package_size` позиции; 1–100000 (`400`, `field: "initial_qty"`). `remaining_qty` 1…initial (`400`, `field: "remaining_qty"`).
- Статус `sealed`, если остаток равен объёму, иначе `open` (`opened_at` = сейчас). Место — как у строки покупки.
- Движение `adjust` (+remaining, `reason: "Начальный остаток"`). `unit_price` у такого экземпляра — `null`.

**Перемещение** `move`: только у `sealed`/`open` (иначе `409 {"error": "Экземпляр уже закончился или списан"}`). Без `location_id` — `400`, `field: "location_id"`. Движение `move` (`qty_delta: 0`, `from_location_id`, `to_location_id`). В то же место — ничего не меняется, движения нет.

**Корректировка** `adjust`: `remaining_qty` 0…initial (`400`, `field: "remaining_qty"`; без поля — тоже `400`), `reason` 0–80 символов. Работает в любом статусе. Движение `adjust` на разницу. `0` → `finished`; больше 0 → `open` (у `sealed`, `finished` и `written_off`). Вернуть в `open` закончившийся или списанный экземпляр, чьё место в архиве, нельзя: `409 {"error": "Место экземпляра в архиве — сначала верните место из архива"}` (в архивном месте не может лежать экземпляров); без места — можно. Ответ — поля `Unit` плюс `movement` — созданное движение (`Movement`, для кнопки «Отменить»); тот же остаток — ничего не меняется, `movement: null`.

**Списание** `writeoff`: только у `sealed`/`open` (иначе `409`). `qty` по умолчанию — весь остаток, иначе 1–100000 (`400`, `field: "qty"`); больше остатка — `409 {"error": "Не хватает: есть 260 мл", "available": 260}`. `reason` 1–80 символов обязателен («Испорчено», «Ошибка ввода»…; `400`, `field: "reason"`). Движение `writeoff`; остаток 0 — `written_off`, частично списанный `sealed` становится `open`. Ответ — поля `Unit` плюс `movement` — движение списания.

Корректировка и списание, как и расход, обновляют экземпляр с условием на прочитанные остаток и статус: если его изменили между чтением и записью — `409 {"error": "Остаток изменился, повторите"}`, ничего не записано.

```json
{ "id": 40, "product_id": 12, "location_id": 5, "initial_qty": 1000, "remaining_qty": 280,
  "status": "open", "opened_at": 1792100000, "created_at": 1791900000, "unit_price": 119000,
  "movement": Movement }
```

## Расход и журнал (ФТ-5.1, ФТ-5.2, ФТ-5.6)

### `POST /api/consume` `{product_id, qty | solution, unit_id?, client_op_id?, occurred_at?}`

Списать `qty` (1–100000, `400`, `field: "qty"`) своей позиции. Вместо `qty` можно передать **раствор** (ФТ-17.2): `solution: {volume_ml, ratio}` — объём готового раствора, мл (1–100000) и пропорция 1:`ratio` (1–1000); сервер сам считает концентрат `max(1, round(volume_ml / (ratio + 1)))` (к ближайшему, половины вверх; 1000 мл 1:10 → 91, 500 мл 1:1 → 250) и списывает его по правилам ниже. Передать и `qty`, и `solution` — `400`, `field: "qty"`; ни одного — `400`, `field: "qty"`; `solution` вне диапазонов или у позиции в шт — `400`, `field: "solution"`. Объём раствора и пропорция записываются в каждое движение расхода (если расход растянулся на несколько экземпляров, у всех одинаковые `solution_ml`/`solution_ratio`), `qty_delta` хранит концентрат.

- Без `unit_id`: сначала вскрытые экземпляры (самый ранний `opened_at`, затем `id`), затем запечатанные — самый старый по дате покупки (у введённых без покупки — по дню создания), затем по `id`. С `unit_id` — начать с него (sealed/open этой позиции; другой позиции или чужой — `404`, закончившийся — `409`), дальше по тому же правилу.
- Не хватает в экземпляре — добирается из следующего. Запечатанный при первом расходе становится `open` (`opened_at` = сейчас); дошедший до 0 — `finished`.
- Всего меньше `qty` — `409 {"error": "Не хватает: есть 260 мл", "available": 260}` и ничего не списывается.
- Одна транзакция, по движению `consume` на каждый затронутый экземпляр, все — одна группа `batch_id`.
- `201 {movements: [Movement], product: ProductSummary, opened_unit_ids: [...], finished_unit_ids: [...], cost: 4760, solution: {volume_ml: 1000, ratio: 10, concentrate: 91} | null}`. `cost` — сумма `cost` движений; `null` — ни у одного нет цены. `solution` — `null`, если расход обычным количеством.
- `Movement` (здесь, в `GET /api/movements` и в карточке позиции) содержит `solution_ml` и `solution_ratio` — раствор, из которого посчитан расход; `null`, если расход обычным количеством или это не расход. Отмена (`revert`) работает как раньше.
- `client_op_id` и `occurred_at` — для расхода без связи, см. «Номер операции и время» ниже.

### Номер операции и время (ФТ-12.4)

`POST /api/consume` и `POST /api/recipes/{id}/apply` принимают два необязательных поля — по ним телефон безопасно отправляет очередь расхода, накопленную без связи.

- `client_op_id` — строка 8–64 символа из `A-Za-z0-9_-` (подходит UUID), иначе `400 {"error": "...", "field": "client_op_id"}`. Номер уникален в пределах пользователя: одинаковые номера у разных пользователей не влияют друг на друга.
- **Повтор.** Если номер уже был выполнен успешно, ничего не списывается, а сервер отвечает `200` с тем же JSON, что и в первый раз (сохранён вместе со списанием, в одной транзакции), и заголовком `X-Garage-Replayed: 1`. Первый ответ — `201`, без заголовка. Тот же номер у другого вида операции (расход и применение шаблона) — `409 {"error": "Этот номер операции уже использован для другого действия", "field": "client_op_id"}`.
- Ошибки (`400`, `404`, `409` нехватки) номер **не запоминают**: после пополнения склада запрос с тем же номером выполнится. Номера хранятся 90 дней, старые удаляются при следующей записи.
- `occurred_at` — когда расходовали, целое, unix-секунды. Этим временем пишутся `created_at` движений (и записи применения шаблона), `opened_at` и `finished_at` экземпляров. Если время позже «сейчас + 5 минут» или раньше «сейчас − 30 дней», оно молча заменяется временем сервера. Без поля — время сервера.

### `POST /api/movements/revert` `{ids: [...]}`

Отмена движений (кнопка «Отменить» и удаление из журнала).

- `ids` — 1–100 различных id (повторы схлопываются), иначе `400`, `field: "ids"`.
- Все или ничего. Хоть один чужой или несуществующий — `404 {"error": "Движение не найдено"}`; разрешены только `consume`, `writeoff`, `adjust` — отмена `purchase` или `move` даёт `409`.
- Остаток экземпляра возвращается на сумму отменённых движений; выход за `0…initial_qty` — `409` («Отмените сначала более поздние движения»). Движения удаляются из журнала.
- Статус после отмены: остаток 0 → `finished` (например, отменён ввод имеющегося остатка); остаток равен объёму и по экземпляру не осталось движений расхода, списания и корректировки → снова `sealed` (`opened_at` = null) — движение «Начальный остаток» вскрытием не считается; иначе → `open` (в том числе `finished`/`written_off` с ненулевым остатком).
- Закончившийся или списанный экземпляр, который ожил бы (остаток больше 0) в архивном месте, — `409 {"error": "Место экземпляра в архиве — сначала верните место из архива"}`, ничего не отменяется.
- `200 {products: [ProductSummary]}` — обновлённые позиции.

### `GET /api/movements[?product_id=&before={id}&limit=50]`

- `200 {movements: [Movement]}` — по `id`, новые сверху. `product_id` — только движения этой позиции (чужая — `404`); `before` — id последнего показанного движения.

Общее для постраничных списков (`/api/purchases`, `/api/movements`): `limit` 1–100, по умолчанию 50, больше — `400`, `field: "limit"`; отрицательный или нечисловой параметр — `400` с `field`.

**Группы движений** (миграция 002, `movements.batch_id`): все движения одного запроса — покупки, расхода, применения шаблона — получают общий `batch_id` (id первого движения); одиночные движения (ввод остатка, перемещение, корректировка, списание) — сами себе группа. У старых записей `batch_id` = собственный `id`.

## Шаблоны расхода (ФТ-8)

```json
// Recipe
{ "id": 2, "name": "Мойка кузова", "sort": 0, "last_used_at": 1792000000, "cost": 41200,
  "items": [{ "product_id": 12, "qty": 40, "solution": null, "product": ProductSummary,
              "available": 2320, "short": false },
             { "product_id": 13, "qty": 91, "solution": { "volume_ml": 1000, "ratio": 10 }, "product": ProductSummary,
              "available": 400, "short": false }] }
// solution — строка задана раствором (ФТ-17.2.4), qty — рассчитанный концентрат; null — задана количеством
// last_used_at — время последнего применения, null — не применяли
// cost — оценка себестоимости по ценам экземпляров, из которых пойдёт списание; null — цен нет
// available — остаток позиции; short — available < qty
```

| Адрес | Что делает |
|---|---|
| `GET /api/recipes` | `200 {recipes: [Recipe]}` — по `sort`, затем `id` |
| `GET /api/recipes/{id}` | `200 {recipe: Recipe}` |
| `POST /api/recipes` `{name, items: [{product_id, qty | solution}]}` | `201 Recipe` (без обёртки). Новый — в конец |
| `PUT /api/recipes/{id}` `{name, items}` | Полная замена имени и строк, `200 Recipe` (без обёртки) |
| `DELETE /api/recipes/{id}` | `204`. Журнал и записи применений не трогаются |
| `POST /api/recipes/reorder` `{ids}` | `204`. `ids` — ровно все шаблоны пользователя по одному разу, иначе `400`, `field: "ids"` |
| `POST /api/recipes/{id}/apply` `{items: [{product_id, qty | solution}], client_op_id?, occurred_at?}` | Применение с поправленными количествами (ФТ-8.2, ФТ-8.4), ответ ниже |

Проверка шаблона: `name` 1–60 символов (`400`, `field: "name"`), уникально без учёта регистра, включая кириллицу (`409 {"error": "Шаблон с таким названием уже есть", "field": "name"}`); `items` — 1–30 строк (`400`, `field: "items"`), `qty` 1–100000 (`field: "qty"`), позиции свои (`404`) и без повторов (`400`, `field: "items"`). Вместо `qty` строка может быть задана раствором `solution: {volume_ml, ratio}` (диапазоны и правила — как у `POST /api/consume`; позиция в шт — `400`, `field: "solution"`): если `solution` передан, `qty` игнорируется, сервер считает концентрат и сохраняет его в `qty` вместе с раствором. Так же — в строках `apply`.

**Применение** `apply`: `items` — 0–30 строк, `qty` 0–100000 (`400 {"error": "Количество — от 0 до 100 000", "field": "qty"}`); `qty` 0 — строка пропускается; позиции — любые свои без повторов, не обязательно из шаблона. Все количества 0 — `400 {"error": "Нечего списывать: все количества равны нулю", "field": "items"}`. Одна транзакция: запись `recipe_runs` + расход по правилам `consume` (движения с `recipe_run_id`, одна группа `batch_id`). **Нехватка не ошибка** (ФТ-8.6): списывается сколько есть. `client_op_id` и `occurred_at` — как у `consume` (раздел «Номер операции и время»).

```json
// 201
{ "run_id": 5, "movements": [Movement], "products": [ProductSummary],
  "shortages": [{ "product_id": 12, "requested": 40, "consumed": 25 }], "cost": 4760 }
```

## Отчёты (ФТ-10.2)

Только чтение, только свои данные. Параметры обоих адресов:

| Параметр | Правило | Ошибка |
|---|---|---|
| `from`, `to` | даты `ГГГГ-ММ-ДД`, обе включительно; обязательны | `400`, `field: "from"` или `"to"` |
| | `from` ≤ `to`; период не больше 5 лет | `400`, `field: "to"` |
| `tz` | необязательно: смещение часового пояса клиента от UTC в минутах (МСК — `180`), −840…840; по умолчанию `0`. Нужен только для расхода: движения хранятся в секундах Unix, и по `tz` сутки периода сдвигаются на местные. Веб-клиент передаёт **текущее** смещение браузера и применяет его ко всему периоду: в зонах с переводом часов движения в пределах часа от границы суток или месяца в прошлом могут попасть в соседний день (для МСК, без перевода, расхождений нет) | `400`, `field: "tz"` |

Деньги — копейки. `by_month` содержит **все** месяцы периода по порядку, в том числе пустые (с нулями), — для столбиков.

### `GET /api/reports/spending?from=&to=` — расходы на покупки (ФТ-10.2.2)

Сумма строк покупок `packages × price_per_package`, чья дата покупки (`purchases.date`) попала в период. Категория — у позиции строки (в том числе архивная), магазин — у покупки.

```json
{
  "total": 253000,                 // 0 — покупок за период нет
  "purchases_count": 2,
  "by_category": [ { "category_id": 3, "name": "Шампуни", "color": "blue", "total": 238000 } ],
  "by_store":    [ { "store_id": 7, "name": "Автохим", "total": 238000 },
                   { "store_id": null, "name": "Без магазина", "total": 15000 } ],
  "by_month":    [ { "month": "2026-09", "total": 238000 }, { "month": "2026-10", "total": 15000 } ]
}
```

`by_category` и `by_store` — по убыванию суммы, затем по названию; пустой период — пустые массивы.

### `GET /api/reports/consumption?from=&to=[&tz=]` — расход (ФТ-10.2.3)

Расход — движения `consume` за период (ручные и по шаблонам); отменённые (`/api/movements/revert`) из журнала удалены и в отчёт не входят. Себестоимость каждого движения — как `Movement.cost` (`|qty_delta| × цена упаковки ÷ initial_qty`, к ближайшему), затем суммируется. Списания (`writeoff`) в расход **не входят**, они отдельным блоком `writeoffs`. Перемещения не учитываются. Корректировки остатка **вниз** (`adjust` с отрицательной `qty_delta`, например потери из инвентаризации) в расход не входят и показываются отдельным блоком `corrections` (по позициям, как `writeoffs`); корректировки вверх в отчёте не показываются.

```json
{
  "total_cost": 33800,             // сумма cost по by_product; движения без цены дают 0
  "by_product": [ { "product_id": 12, "name": "Шампунь", "unit": "ml", "qty": 100, "cost": 23800 } ],
  "by_month":   [ { "month": "2026-10", "cost": 33800, "qty_ml": 100, "qty_pcs": 2 } ],
  "writeoffs": {
    "by_product": [ { "product_id": 12, "name": "Шампунь", "unit": "ml", "qty": 50, "cost": 11900 } ],
    "cost": 11900
  },
  "corrections": {                 // корректировки остатка вниз, не входят в расход
    "by_product": [ { "product_id": 12, "name": "Шампунь", "unit": "ml", "qty": 100, "cost": 20000 } ],
    "cost": 20000
  }
}
```

- `by_product`, `writeoffs.by_product` и `corrections.by_product`: `qty` — мл или шт по `unit` позиции; `cost` — `null`, если ни у одного движения позиции нет цены (экземпляр введён без покупки). Порядок: по убыванию `cost` (без цены — в конце), затем по `qty`, затем по названию.
- `by_month`: `qty_ml` и `qty_pcs` считаются отдельно (мл и штуки не складываются).
- Месяц движения определяется по местному времени (`tz`).

### История цены позиции (ФТ-10.2.4)

Отдельного адреса нет: `GET /api/products/{id}` уже отдаёт `purchases` (последние 20 покупок, новые сверху) с `price_per_100` (мл) или `price_per_unit` (шт) по каждой дате — график строится по ним.

## Экспорт и импорт (ФТ-10.3)

Все адреса работают только с данными вошедшего пользователя. Скачивание — обычные `GET`: подходит ссылка `<a href download>`, cookie сессии уходит сама. Ответ — файл (`Content-Disposition: attachment`, `Cache-Control: no-store`), а не JSON API.

- Время (`*_at`) — секунды Unix (UTC); даты покупок — `ГГГГ-ММ-ДД`; деньги — копейки; количество — целые мл или шт.
- `id` — прежние номера из базы. Они нужны только как ключи связей внутри файла (`category_id`, `unit_id`, `batch_id` и т. д.); при импорте база выдаёт новые.
- `batch_id` движения — `id` первого движения той же группы (одна покупка, одно нажатие «Списать», одно применение шаблона).
- Пустые списки — `[]`. Лишние поля при импорте игнорируются.
- Версия 2 (v1.5, ФТ-15.6.1) добавила `purposes` и поля позиции `purpose_ids`, `ph`, `incompatible`, `instruction`, `rating`, `do_not_buy`. В файле версии 1 их нет: импорт принимает такой файл, у позиций новые поля пусты, а стартовые назначения, уже созданные у пользователя, остаются нетронутыми.
- Версия 3 (v1.6, ФТ-17.2.6) добавила поле позиции `dilutions` (`[{name, ratio}]` по порядку) и поля `solution_ml`/`solution_ratio` в движениях и строках шаблонов. В файлах версий 1 и 2 их нет: импорт принимает такие файлы, пропорций и раствора не будет.

### `GET /api/export/products.csv`, `/purchases.csv`, `/movements.csv` — таблицы (ФТ-10.3.2)

Имя файла: `garage-<логин>-<products|purchases|movements>-<ГГГГ-ММ-ДД>.csv`. Для Excel в русской локали: UTF-8 с BOM, разделитель `;`, строки через CRLF, даты `ДД.ММ.ГГГГ`, деньги в рублях с запятой (`1190,50`), количество — целые числа. Значения, начинающиеся с `=`, `+`, `-`, `@`, табуляции или возврата каретки, получают в начале апостроф (защита от CSV-инъекций); числа, которые формирует сервер (например `-250`), не экранируются.

- `products.csv` — позиции с остатками: Название; Бренд; Категория; Единица (мл/шт); Объём упаковки; Остаток; Экземпляров; Минимальный остаток; Ниже минимума; Места; Штрихкод; Заметка; В архиве; **Назначения** (через запятую, по порядку справочника); **pH** (с запятой, `7,3`); **Оценка** (1–5, пусто — нет); **Не брать больше** (да/нет). Остаток — сумма по действующим экземплярам (запечатанным и вскрытым).
- `purchases.csv` — строки покупок, одна строка таблицы на строку покупки: Дата; Магазин; Позиция; Бренд; Упаковок; Цена за упаковку, руб; Сумма, руб; Заметка.
- `movements.csv` — журнал: Дата и время; Тип (Покупка, Расход, Списание, Перемещение, Корректировка); Позиция; Бренд; Изменение; Единица; Откуда; Куда; Причина; Стоимость, руб (по цене экземпляра, пусто без покупки); **Раствор, мл** (объём раствора, пусто — расход не раствором); **Пропорция 1:N** (только число N — «1:10» Excel принял бы за время; пусто — не раствор). Расход шаблона при нехватке концентрата пишется без раствора: списано меньше, чем требует раствор. Время — по часовому поясу из необязательного `?tz=` (минуты от UTC, МСК = 180; по умолчанию UTC).
- Неверный `tz` — `400`, `field: "tz"`.

### `POST /api/import` — загрузка файла экспорта (ФТ-10.3.3)

Тело — JSON файла `export.json` **как есть**. Требуется заголовок `X-Requested-With: garage`.

**Предел тела — 100 МБ** (только на этом адресе; на остальных — 64 КБ). Больше — `413 { "error": "Файл больше 100 МБ" }`. Обратному прокси (nginx) для `/api/import` нужны `client_max_body_size 100m`, `client_body_timeout 120s`, `proxy_read_timeout`/`proxy_send_timeout` 600s и `proxy_request_buffering off` (см. `deploy/garage.nginx.conf`). Срок чтения тела на сервере — 10 минут, записи ответа — 12 минут.

**Один импорт за раз на весь сервер.** Пока идёт чужой или свой предыдущий импорт, новый получает `409 { "error": "Импорт уже идёт. Подождите, пока он закончится, и повторите" }`. Непустой склад отклоняется (`409`) **до чтения тела**, ещё раньше проверки файла: при непустом складе даже битый файл получит `409`, а не `400`.

- `200 { "imported": { "categories": 11, "locations": 2, "stores": 1, "purposes": 7, "products": 2, "units": 9, "purchases": 2, "purchase_lines": 3, "movements": 11, "recipes": 1, "shopping": 1 } }` — счётчики записей файла.
- `409` — склад не пуст: у пользователя есть хотя бы одна **позиция** (в том числе архивная), **покупка** или **движение**. Только эти три вида считаются; текст объясняет, что делать («Импорт возможен только в пустой склад…»). Стандартные категории, созданные при регистрации, места, магазины, шаблоны расхода и пункты списка покупок пустоту не нарушают: категории, места и магазины сливаются по имени, пункты списка дописываются, а шаблон с названием, которое у пользователя уже есть, даёт `400` (`recipes[i].name`) и полный откат. Сверка пустоты повторяется внутри транзакции записи: два параллельных импорта в одного пользователя дадут один `200` и `409`.
- `409` — «Импорт уже идёт» (см. выше).
- `400 { "error": "products[3].name: Название — от 1 до 80 символов", "field": "products[3].name" }` — файл не прошёл проверку; `field` и начало текста указывают место в файле. Если файл не удалось прочитать как JSON, `field` нет; если тип значения неверен, `field` — путь поля (`products.name`).

Проверка (всё до записи, ничего не пишется при первой же ошибке):
- `format` равен `"garage-export"`, `version` равен `1`, `2` или `3`; иначе `400` с `field: "format"` / `"version"`;
- значения — по тем же правилам, что у обычного API: длины названий и заметок, единица `ml`/`pcs`, размер упаковки, штрихкод, цвета категорий, ссылки магазинов, дата покупки, `packages` 1…100, цена 0…1 000 000 ₽, количество 1…100 000, до 30 строк в покупке и шаблоне, причина до 80 символов;
- каждая ссылка (`category_id`, `store_id`, `product_id`, `unit_id`, `purchase_line_id`, `location_id`, `recipe_run_id`, `batch_id`) указывает на `id` **внутри файла**; `id` в пределах вида уникальны и положительны; названия категорий, мест, магазинов и шаблонов не повторяются без учёта регистра;
- экземпляр: `0 ≤ remaining_qty ≤ initial_qty`, статус `sealed`/`open`/`finished`/`written_off`, строка покупки относится к той же позиции; знак `qty_delta` соответствует типу (приход > 0, расход и списание < 0, перемещение 0);
- **сверка остатков**: у каждого экземпляра `remaining_qty` равен сумме `qty_delta` его движений (первое движение — покупка или «Начальный остаток» — уже содержит стартовый объём, поэтому `initial_qty` к сумме не добавляется; экземпляр без движений допустим только с нулевым остатком). Иначе `400`, `field: "units[i].remaining_qty"`;
- **статус и остаток**: `sealed` — `remaining_qty == initial_qty` и `opened_at` пуст; `open` — `remaining_qty > 0`; `finished` и `written_off` — `remaining_qty == 0` и задан `finished_at`. Ошибка — `400` с путём `units[i].<поле>`;
- **число записей** не больше: движений 200 000, экземпляров 50 000, покупок 20 000 (строк покупок 60 000), позиций 10 000; категорий, мест, магазинов, шаблонов, применений шаблонов и пунктов списка покупок — по 10 000. Иначе `400` с `field` — именем списка (`movements`);
- версия 2: `ph` — 0–14 с одним знаком, `rating` — 1–5, `incompatible` до 300 и `instruction` до 2000 символов, `purpose_ids` — `id` назначений из файла без повторов (до 50 у позиции; ошибка — `field: "products[i].purpose_ids[j]"`), названия назначений не повторяются без учёта регистра; назначений в файле — не больше 10 000;
- версия 3: у позиции в мл — до 10 пропорций, `name` 1–40 символов, `ratio` 1–1000 (ошибка — `field: "products[i].dilutions"`), у позиции в шт пропорций нет; `solution_ml` (1–100 000) и `solution_ratio` (1–1000) в движении или строке шаблона задаются вместе или оба `null` (ошибка — `field: "movements[i].solution_ml"` и т. п.);
- `sort` категорий, мест и назначений — целое от −1 000 000 000 до 1 000 000 000.

Запись — одна транзакция: при любой ошибке в складе ничего не меняется. Категории, места, магазины и назначения, чьё имя совпадает (без учёта регистра) с уже имеющимся, **сливаются** (цвет, порядок, архивность берутся из файла); остальные создаются. Все прочие записи получают новые `id`, связи и группы движений (`batch_id`) переносятся. Шаги кнопок из `settings` заменяют текущие. Фото из `products[].photo` сохраняется с той же проверкой, что у `PUT /api/products/{id}/photo`: base64, не больше 400 КБ, тип по содержимому (поле `mime` не принимается на веру), не больше 4096 × 4096 px. Ошибка — `400` с `field: "products[3].photo"` (или `…photo.data`, если это не base64). Файлы с фото крупнее: каждое до 400 КБ + треть на base64 (до ~0,5 МБ на позицию); общий предел 100 МБ остаётся, для больших складов есть экспорт без фото.

## Telegram-бот (ФТ-11)

Сам бот на этих адресах не работает: он опрашивает Telegram сам (`getUpdates`). Адреса нужны экрану «Ещё → Профиль → Telegram». Токен бота в API не передаётся никогда; он лежит только в `/etc/garage/config.json` (`telegram.token`), пустой токен отключает бота. Служебные таблицы привязки в экспорт и импорт не входят.

### `GET /api/telegram`

- `200 { "enabled": true, "bot_username": "garage_bot", "linked": true, "telegram_name": "Иван П", "linked_at": 1792000000 }`.
  - `enabled` — бот включён в конфигурации (задан токен).
  - `bot_username` — имя бота без `@`; `null`, если бот выключен или ещё не назвался (первый `getMe` не удался).
  - `linked` — к пользователю привязан Telegram-аккаунт; `telegram_name` и `linked_at` (секунды Unix) — `null`, пока не привязан.

### `POST /api/telegram/link`

Выдаёт одноразовую ссылку привязки. Тело пустое (`{}`), нужен заголовок `X-Requested-With: garage`.

- `200 { "url": "https://t.me/garage_bot?start=<код>", "expires_at": 1792000600 }` — код: 32 случайных байта в base64url (43 символа, только `A-Za-z0-9_-`), действует 10 минут (`expires_at`, секунды Unix). В базе хранится только sha256-хеш кода. Новая ссылка гасит прежнюю неиспользованную.
- `503 { "error": "Бот не настроен" }` — бот выключен или его имя ещё неизвестно.

Привязка завершается в Telegram: пользователь переходит по ссылке, бот получает `/start <код>` **в личном чате** и связывает аккаунт. Код одноразовый. Один аккаунт Telegram — один пользователь сайта, новая привязка заменяет старую. Чтобы увидеть результат, сайт повторяет `GET /api/telegram`.

### `DELETE /api/telegram`

Отключает Telegram: удаляет привязку, неиспользованные коды и сведения о позициях, по которым уже сообщалось о минимуме. Нужен заголовок `X-Requested-With: garage`.

Уведомление «Заканчивается» (ФТ-11.7, ФТ-15) не отправляется по позициям с `do_not_buy`, состояние минимума по ним не копится; если в наличии есть аналоги, в конец добавляется строка «Есть дома для того же: А, Б» (до 3).

- `204` — готово; если привязки не было, ответ тот же.

## Погода (ФТ-16)

Прогноз Open-Meteo запрашивает сервер: браузер к внешним адресам не обращается. Место по умолчанию — `weather.default` в конфигурации (`{"name", "lat", "lon"}`, на relay — Донецк); `weather.base_url` и `weather.geocoding_url` пусты и означают стандартные адреса Open-Meteo (задаются для тестов). Пользователь может выбрать своё место. Нет ни своего места, ни места по умолчанию — погода ему выключена. Часы и дни прогноза — в часовом поясе `weather.timezone` (по умолчанию `Europe/Moscow`; `auto` — по координатам, но для Донецка Open-Meteo выбирает Europe/Kyiv). `utc_offset` в ответе — смещение этого пояса. Подпись на экранах: «Погода: Open-Meteo.com» (CC BY 4.0). Таблица места (`weather_places`) служебная и в экспорт и импорт не входит.

Сервер держит прогноз в памяти по месту (координаты с точностью 0,01°): обновление не чаще раза в час, одновременные запросы к одному месту схлопываются в один. Прогноз старше часа отдаётся сразу, а обновляется в фоне; `stale: true` ставится, когда прогнозу больше 3 часов (обновить не удалось). Ждать Open-Meteo приходится только при первом запросе места. После сбоя сервер минуту не повторяет запрос. Запрашивается 9 дней, отдаётся 7: два лишних нужны, чтобы окно «после» у последнего дня не упиралось в край прогноза. Правила оценки и пороги — `internal/weather/rules.go`.

### `GET /api/weather`

Без параметров — прогноз города по умолчанию. С `?lat=&lon=&name=` — прогноз любого города (просмотр на экране «Погода»): город по умолчанию не меняется, в ответе `"preview": true`, `location.custom` — `false`. Неверные координаты — `400` (`field`: `lat` или `lon`), пустое имя — `400` (`field`: `name`). Больше 30 просмотров в минуту на пользователя — `429` с `Retry-After`; прогноз города по умолчанию этим лимитом не ограничен.

- `200`:

```json
{
  "enabled": true,
  "location": { "name": "Донецк", "lat": 48.023, "lon": 37.802, "custom": false },
  "fetched_at": 1793355600,
  "stale": false,
  "utc_offset": 10800,
  "days": [
    {
      "date": "2026-10-30", "weekday": "пт",
      "t_min": 7.3, "t_max": 15.5, "precip_mm": 0, "precip_prob": 18, "code": 3,
      "wash": { "level": "bad", "reasons": ["дождь завтра в 01:00"] },
      "coat": { "level": "good", "reasons": [] }
    }
  ],
  "today_hours": [
    { "time": "15:00", "temp": 15.4, "precip_mm": 0, "precip_prob": 0, "wind": 4.9, "humidity": 46, "code": 3 }
  ],
  "best": { "wash": "2026-11-01", "coat": null }
}
```

  - `enabled` — погода включена для пользователя. `false`: `location` и `fetched_at` — `null`, `days` и `today_hours` — `[]`, `best` — `{"wash": null, "coat": null}`; запрос наружу не делается.
  - `location.custom` — `true`, если место выбрал сам пользователь.
  - `fetched_at` — когда получен прогноз (секунды Unix); `stale` — прогнозу больше 3 часов, свежий получить не удалось.
  - `utc_offset` — смещение места от UTC в секундах (`utc_offset_seconds` ответа Open-Meteo; Донецк — `10800`); по нему интерфейс считает «сегодня» и текущий час места, в том числе без связи. При `enabled: false` — `0`.
  - `days` — до 7 дней, начиная с сегодняшнего (прошедшие дни устаревшего прогноза отбрасываются). `weekday` — `пн`…`вс`. `t_min`, `t_max` — °C; `precip_mm` — сумма за сутки; `precip_prob` — наибольшая вероятность осадков за сутки, %; `code` — код погоды WMO.
  - `wash` (мойка) и `coat` (покрытие: воск, керамика, силанты) — `level`: `good` | `meh` | `bad`; `reasons` — причины по-русски (у `good` пусто; у `bad` до 3, у `meh` — мягкие: вероятность осадков 30–50 %, влажность 80–90 %). Оценка считается по светлому времени 8:00–20:00. Сегодня учитываются только оставшиеся часы; если светлое время закончилось — `bad` с причиной «светлое время уже закончилось».
    - Мойка хороша, если в светлое время вероятность осадков ниже 30 %, нет часа с осадками от 0,2 мм, температура выше +2 °C, ветер слабее 10 м/с и ближайшие 24 часа после 20:00 без дождя.
    - Покрытие хорошо, если в светлое время есть окно для нанесения: 3 часа подряд при +5…+30 °C и влажности ниже 80 % (80–90 % — `meh`, если лучшего окна нет), и 48 часов с начала окна без осадков. Окна нет — `bad` с причиной по самому близкому к норме часу («влажность весь день выше 90 %», «холодно +3° весь день», «нет окна на 3 часа подряд»). Сегодня окно ищется среди оставшихся часов.
    - Нет данных: если осадки или их вероятность в ответе пусты (`null`), час не считается сухим — оценка не выше `meh` с причиной «нет данных об осадках». Если окно «после» (24 ч для мойки, 48 ч для покрытия) выходит за последний час прогноза, оценка не выше `meh` с причиной «нет прогноза на сутки вперёд» / «нет прогноза на 2 суток вперёд»; такой день не бывает лучшим (`best`).
    - Причины: «дождь в 15:00», «снег завтра в 12:00», «мороз −3°», «холодно +2°», «жара +33°», «ветер 12 м/с», «влажность 92 %», «вероятность осадков 40 %».
  - `today_hours` — 24 часа сегодняшних суток (`time` — `ЧЧ:00`): `temp` °C, `precip_mm` за час, `precip_prob` %, `wind` м/с, `humidity` %.
  - `best` — ближайший (включая сегодня) день с оценкой `good`, `ГГГГ-ММ-ДД`, или `null`.
- `502 { "error": "Прогноз сейчас недоступен" }` — Open-Meteo не отвечает и прогноза в памяти нет.

### `GET /api/weather/places?q=` — поиск города

- `q` — название, 2–60 символов (иначе `400` с `field: "q"`).
- `200 { "places": [ { "name": "Донецк", "admin1": "Донецкая область", "country": "Украина", "lat": 48.023, "lon": 37.802 } ] }` — до 8 мест (геокодер Open-Meteo, язык `ru`); `admin1` и `country` отличают одноимённые города, могут быть пустой строкой. Ничего не найдено — `[]`.
- `429` — больше 30 поисков в минуту на пользователя; заголовок `Retry-After` и `retry_after` (секунды).
- `502 { "error": "Поиск города сейчас недоступен" }` — геокодер не ответил.

### `PUT /api/weather/location` `{name, lat, lon}` — своё место

- `name` — 1–80 символов без управляющих (пробелы по краям убираются), `lat` — от −90 до 90, `lon` — от −180 до 180; оба числа обязательны. Ошибка — `400` с `field` (`name`, `lat` или `lon`).
- `429` — больше 10 смен места в минуту на пользователя (`Retry-After`, `retry_after`); сброс (`DELETE`) лимитом не ограничен.
- `200 { "name": "Ростов-на-Дону", "lat": 47.2313, "lon": 39.7233, "custom": true }`. Место у каждого пользователя своё; новое заменяет прежнее.

### `DELETE /api/weather/location` — вернуться к месту по умолчанию

- `204`; если своего места не было, ответ тот же. Без места по умолчанию в конфигурации погода пользователю выключается.

Бот: команда `/weather` (и слово «погода») отвечает оценкой на сегодня и завтра и ближайшими хорошими днями для места привязанного пользователя (ФТ-16.3.3); сам о погоде не пишет.

## Служебное

### `GET /api/health` — без входа

- `200 { "status": "ok", "version": "…" }` — версия сборки (`dev` при сборке без версии).

## Командная строка (ФТ-1.2)

```
garage [-config /etc/garage/config.json]                        # запустить сервер
garage -config /etc/garage/config.json user add <логин> [-owner] # создать пользователя
garage -config /etc/garage/config.json user passwd <логин>       # задать новый пароль
garage -config /etc/garage/config.json user list                 # логины, владелец, дата создания
garage -version                                                  # показать версию
```

- `-config` указывается до `user`; по умолчанию — `/etc/garage/config.json`.
- Пароль читается из терминала без отображения, дважды. Если ввод не терминал — одна строка из stdin (для скриптов).
- `user add`: логин и пароль проверяются по тем же правилам, что в API. **Первый** созданный пользователь становится владельцем, следующие — нет; флаг `-owner` делает владельцем явно. Настройки и категории по умолчанию заполняются так же, как при приглашении.
- `user passwd`: сбрасывает **все** сессии пользователя.
- `user list`: таблица «ЛОГИН / ВЛАДЕЛЕЦ / СОЗДАН» (время — местное).
